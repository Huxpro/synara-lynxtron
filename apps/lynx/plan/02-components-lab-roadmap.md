# Components Lab convergence roadmap

Status: active standing P0

Current coverage (2026-09-09): 38 shared story identities and 38/38 real paired
Electron/Lynx renderers. The original 15 high-risk product stories are joined by
Button, Input, Menu, Dialog, Tooltip, Kbd, Collapsible, Command, and ScrollArea
and shared Switch/Checkbox/IconButton/Textarea/loading/Separator/Badge/TimePicker/Alert primitive matrices. CL-M0/M1 are complete for
the seed inventory; CL-M2
has a working paired shell, deterministic story/state contract, and native OS
`View → Components Lab…` entry in both desktop apps. Theme/viewport automation,
numeric parity gates, and the full Native interaction matrix remain open.

## Objective

Build paired Electron and Lynxtron component laboratories that make renderer
fidelity deterministic below the page level. Both Labs consume one manifest of
stable stories. A product surface may not substitute a different interaction
primitive merely because it is easier in one renderer.

The first canonical regression is `editor-rail/add-menu`: Electron renders an
anchored menu containing `New chat` and `New terminal`; Lynxtron currently opens
a modal. The Lab must make that component-identity mismatch visible before the
product path is certified.

## Non-negotiable contracts

- Electron remains the UI/UX authority.
- A story ID describes a product component contract, not a screenshot.
- Electron and Lynx stories use the same fixture/state/theme/viewport identity.
- Reuse is auditable: one Electron component reused by N consumers maps to one
  Lynx counterpart reused by the corresponding N consumers.
- Renderer-local variants require a named platform limitation and evidence.
- The Lab uses real product components and callbacks; mock-only replicas do not
  count as coverage.
- Browser-first evidence accelerates iteration; Native remains mandatory for
  focus, pointer, textarea/IME, menus, accessibility and host integration.
- Every fidelity goal loop updates the Lab inventory and coverage ledger.

## Story contract

Each story must declare:

- `id`, `title`, `category`, and owning product component identity;
- Electron renderer entry and Lynx renderer entry;
- known consumers in both renderers;
- fixture ID and deterministic setup action;
- variants and states, including interaction state where applicable;
- theme and viewport matrix;
- geometry, color, typography, accessibility and interaction assertions;
- platform deltas with rationale and upstream issue/evidence when applicable.

## Milestones

### CL-M0 — Inventory and identity graph

- Inventory Electron components, shared compositions, Lynx adapters/primitives,
  and their import/consumer graph.
- Assign stable IDs to primitives and high-risk composites.
- Produce a machine-readable missing/many-to-one/one-to-many mapping report.
- Seed with menus, dialogs, popovers, inputs, buttons, toggles, model picker,
  EditorRail add menu, Add Action editor, context-window meter, terminal search,
  Explorer controls, and right-dock tabs.

Acceptance: the report identifies known FC-029/031/032/033 component ownership
and flags EditorRail add menu as a modal-vs-menu mismatch.

Current gate: `bun run --cwd apps/lynx audit:component-lab` validates every
manifest authority module/component, the symbol actually mounted by each Lab
renderer, and at least one non-test product consumer. Its first run exposed ten
stale conceptual identities; the manifest now names the actual shared menu,
action editor, navigation-row, message-action, and semantic-tone boundaries.
The current 41-story catalog passes all 82 renderer mappings.
Its normalized renderer × variant × theme × viewport × state matrix contains 2,936 meaningful cells after removing duplicated variant/state axes;
22 stories have explicit interactive states. This count is generated by
`summarizeComponentLabCoverage`, not maintained by hand.
The machine-readable primitive inventory currently reports 37 Electron UI
modules, 22 Native UI modules, 21 covered counterpart pairs, and 16 explicit
adapter mappings with evidence and rationale. Both
`counterpartNotInLab` and `missingLynxCounterpart` are zero.

### CL-M1 — Shared manifest and deterministic fixtures

- Add schema-only story contracts to `packages/contracts`.
- Add runtime manifest/fixture helpers to `packages/shared` with explicit exports.
- Define stable fixture payloads without direct SQLite mutation.
- Add manifest validation and duplicate/missing renderer tests.

Acceptance: one command lists stories and fails for missing renderer entries,
duplicate IDs, missing states, or fixture drift.

### CL-M2 — Paired Lab shells

- Add internal Electron/Web and Lynx Components Lab routes as renderer
  implementation details.
- Expose the user-facing desktop entry in both apps through the native OS
  `View → Components Lab…` menu; desktop users must not need a URL.
- Use the same story/category/state query contract and navigation anatomy.
- Support theme, viewport, state, interaction, and fixture controls.
- Keep Lab code out of normal product bundles when practical.

Acceptance: the same story ID opens in both renderers and reports identical
fixture/state metadata.

Runtime isolation: the Lab route suppresses global Offline/Reconnecting chrome
and disables the route-level threads query/orchestration subscription. Its
deterministic fixtures therefore render without a live Synara server and do not
emit reconnect traffic.

Harness ownership also covers the Electron side: before replacing the isolated
comparison profile, the launcher terminates only an Electron command whose
executable and exact `--user-data-dir` both match that profile. This prevents a
stale comparison instance from accepting the new launch through Electron's
single-instance path while leaving ordinary Synara and unrelated Electron apps
untouched.

### CL-M3 — Core primitive catalog

- Button, icon button, input, textarea, checkbox/radio/switch.
- Menu, submenu, context menu, command palette, popover/tooltip.
- Dialog/modal, alert/notification, disclosure/collapsible.
- Tabs, segmented controls, list rows, badges, keyboard hints, scroll containers.
- Every interactive story covers default, hover, focus, pressed, disabled and
  keyboard behavior where meaningful.

Acceptance: paired geometry/token assertions and focused tests pass in light and
dark at 1280x820 and 1440x900.

### CL-M4 — Product composite catalog

- Composer model/effort picker and provider/model submenus.
- Context-window meter/card, voice states, permission controls.
- EditorRail tabs and add menu, RightDock tabs/add menu.
- Add Action trigger/editor and action rows.
- Explorer search/tree/tab/header/error; diff headers/toolbars; terminal controls.
- Sidebar project/thread rows and context menus; transcript message/tool rows.

Acceptance: every open fidelity item references at least one Lab story and every
fixed story is consumed by the actual owning product surfaces.

### CL-M5 — Automated parity gates

- Capture paired screenshots and numeric box/style/accessibility probes.
- Compare named states with configurable tolerances and intentional-delta files.
- Require clean renderer console and exact fixture metadata.
- Enforce browser ownership cleanup and the existing exact-owned Native rules.
- Keep local retained screenshots below the repository limit.

Acceptance: CI/local command emits pass/fail by story/state/theme/viewport and a
human-readable residual report.

### CL-M6 — Consumer reuse enforcement

- Build an import/consumer graph for mapped components.
- Flag local components that duplicate a mapped primitive or composite.
- Add source-level guards for known mistakes (menu replaced with dialog, one
  shared Electron component mapped to multiple ad-hoc Lynx implementations).
- Migrate product consumers to the canonical mapped component.

Acceptance: EditorRail add control, model picker, Add Action flow, context meter,
and other seeded consumers pass the reuse audit.

Current gate: the component-Lab identity audit reports renderer-specific product
consumer counts and requires explicit, reviewable overrides for the few stories
that intentionally mount a production wrapper or represent a token contract.
It also emits 38 machine-readable counterpart groups and enforces the mapping in
both directions: one Electron identity cannot fan out to multiple Native
counterparts, and a Native identity cannot collapse multiple Electron identities
without an exact allowlist, rationale, and evidence. The sole current many-to-one
group is the intentional project/thread convergence on the shared Native
`SidebarNavigationRow` shell; the two specimens retain independent content and
action anatomy. This closes the seed catalog's counterpart graph baseline; broad
duplicate-component detection outside the catalog remains open.

### CL-M7 — Native certification and ongoing governance

- Batch real pointer/keyboard/focus/IME/accessibility/menu verification.
- Certify restart/persistence and host-integrated stories.
- Add a pull-request checklist and goal-loop ledger update requirement.
- Track story totals, covered states, open residuals and platform boundaries.

Acceptance: new component fidelity work cannot be marked complete without an
updated Lab story or an explicit documented exemption.

## Goal-loop ledger

Every continuation must record:

1. stories added or updated;
2. consumer mappings changed;
3. paired states newly verified;
4. unresolved component-identity mismatches;
5. Native-only boundaries and next certification cells.

  semantic icon tones, and the shared command palette.
